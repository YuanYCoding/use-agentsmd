# 使用示例

以下是调用方式和预期行为的说明性示例。路径、命令和技术栈必须按真实项目核实，不能直接作为所有项目的规则。

## 搭建后校准

```text
$use-agentsmd

项目已经完成脚手架搭建，开发服务器可以正常启动。
请核对实际目录、依赖管理和运行命令，校准 AGENTS.md。
```

应核对清单和脚本，并区分“用户已确认启动”与“本次自行运行验证”。缺少测试脚本时，不应补一个虚构命令。

## 已上线项目第一次补建

```text
$use-agentsmd

这是正在维护的服务，目前没有根 AGENTS.md。
请按项目当前情况创建，重点参考现有运维文档和发布流程。
```

应进入维护阶段的创建分支。部署工作流存在只能证明配置存在，不能据此推断线上状态，也不应自动触发发布。

## 将明确的长期纠正写入规则

```text
$use-agentsmd

我们已决定：后续新增删除确认弹窗都复用现有 ConfirmDialog。
请核实组件位置，把这条约定按实际范围写入项目说明。
```

合适的条目会包含触发场景、实际组件路径和必要原因。它不会自动扩大成“全项目禁止新增组件”。

## 检查后无需修改

```text
$use-agentsmd

这次仅把按钮文案从保存改成了立即保存。
请进行一次收尾维护检查。
```

若没有新的长期约定，保留原文件内容与修改时间。交付时说明无需修改即可。

## monorepo

```text
$use-agentsmd

目标是整个仓库。前端与后端已有不同的开发流程，
请检查根目录公共规则和相关子目录规则是否准确。
```

应先确认根目录、包名和作用域。共享要求保留在根文件，真正不同的规则才进入对应模块；相对链接按所属 AGENTS.md 的位置解析。

## 一个准确的命令说明

假设项目配置已证明脚本只做类型检查：

```markdown
## 验证
- 从仓库根目录运行 `npm run check:types --workspace @desk/client`，检查 Web 模块类型。
- 此检查不覆盖交互和接口行为；相关验证按项目现有流程执行，并说明实际结果。
```

这里演示的是执行目录、真实目标和覆盖范围的表达方式。具体工具、脚本和要求来自目标项目。
