# use-agentsmd

维护一份简短、准确、能让下一位 AI 接着工作的项目说明。采用“开工前建简版、跑通后校准、长期约定变化时更新”的节奏。文件名统一为 `AGENTS.md`。

## 先确认项目与操作模式

1. 根据用户指定路径、当前任务和工作目录定位目标项目。Git 根目录、工作区配置、项目清单和 README 用来交叉确认；在多项目目录或 monorepo 中，不把任意当前子目录或外层容器目录直接当作目标根目录。若仍有多个合理目标，先询问目标项目，继续进行不依赖该选择的只读检查。
2. 读取适用的上级说明、目标根目录的 `AGENTS.md`，以及与本次范围有关的子目录说明。对已有文档引用的规则文件，按当前工具支持的方式读取；保留引用和原有职责划分，不把 `@路径` 当作所有工具都支持的通用语法。
3. 检查目标根目录的精确文件名，决定操作模式：
   - **不存在 `AGENTS.md`：创建。** 这是本次管理的创建分支；文件缺失不能证明项目刚开始，也不能证明历史上从未调用过 Skill。先判断实际阶段，再创建相应内容。
   - **已存在 `AGENTS.md`：更新或保持不变。** 先读取全文，对照证据做最小必要修改；无有效变化时保持文件及其时间戳不变。
   - 仅存在 `AGENT.md` 等旧名称时，先读取并核实可复用内容，再创建规范名称的文件。保留旧文件及已有调用关系；重命名、删除或迁移引用只在任务明确包含迁移时处理，并在交付中说明遗留入口。
   - 如果文件是符号链接或其他转发入口，先确认真实目标和共享范围，保留入口结构，避免把单个项目规则写入多个项目共享的文件。
4. 此 Skill 的默认写入范围是目标项目的根 `AGENTS.md`。确有模块独有规则时，才考虑在相关子目录增加或更新同名文件。保持现有语言、组织风格和换行习惯；新文件默认使用用户的语言。

调用 Skill 已包含对目标项目创建或维护说明文件的授权，按上述范围直接完成。用户只要求分析、检查或提供草稿时，遵守其只读范围。不要顺带修改业务代码、CI、依赖、全局规则或其他工具配置。

## 用证据识别阶段

先查看已有上下文，再按需读取项目清单、锁文件、目录、关键模块、脚本、测试和 CI 配置、需求/架构/运维文档，以及当前相关差异。避免扫描依赖、构建产物和无关目录。

将**项目整体成熟度**与**当前任务阶段**分开判断。例如，已上线项目正在替换鉴权模块，应保留维护阶段的公共要求，同时更新重构涉及的约定。阶段不是只能向前推进的流水线；不同模块可以处于不同阶段。

| 当前阶段 | 可用判断依据 | 本次重点内容，仅在实际存在时写入 |
| --- | --- | --- |
| 开工／想法已进入实现 | 用户准备开始实际开发；目录为空或仅有需求、设计草稿 | 项目目标、明确的首期范围、已确认的技术选择、工作边界、必要的文档入口 |
| 搭建／首次跑通 | 已有脚手架、依赖、入口或启动结果；核心业务尚未验证 | 实际目录职责、包管理器、安装和启动方式、现有检查命令、必要环境配置入口 |
| 首个可用版本 | 核心业务链路已经实现，且有用户确认或可对应的验证结果 | 已形成的代码组织方式、公共组件/工具、接口与数据约定、核心流程验证入口 |
| 持续迭代 | 在已有功能上增加或修正能力 | 会影响后续开发的新约定、模块职责变化、复用入口、相关验证要求；通常局部修改 |
| 重构／切换方案 | 技术栈、目录、依赖管理、接口契约或工作流程正在改变 | 区分迁移目标与当前可用事实；随着实现落地替换旧说明，处理受影响的引用和失效规则 |
| 上线／维护 | 正在准备发布，或有明确运行维护背景与相关证据 | 已存在的验证和部署入口、运维文档、配置说明、适用操作要求；有依据时引用回滚与故障处理流程 |

判断时遵守以下区别：

- 用户确认的设计选择可以记为约定，但不要写成已经实现。项目文件、脚本或部署配置存在，只能证明对应内容已定义，不能证明启动成功、业务可用或线上已部署。
- 既有文档和历史聊天可提供线索；涉及当前路径、命令、依赖或运行状态时，检查实际拥有这些信息的文件或最近有效结果。
- 没有运行结果时，不宣称“已验证通过”。不要为了判断阶段而安装依赖、启动长期服务、访问生产环境或执行部署。
- 阶段证据不足时，采用能支持的内容范围，并在交付中简述判断依据及局限。只有缺失信息会实质改变目标、规则含义或写入范围时才询问；可完成的部分继续处理。

## 筛选值得长期保存的内容

对每个候选条目判断：**下一位没有参与本次开发的 AI，不知道它会不会做错、重复探索或破坏已有约定？它是否已有依据，并会持续适用？**

- 纳入：实际使用方式变化、明确的公共开发约定、经核实的项目特有易错点、用户对后续行为的长期纠正、重要文件的阅读入口。
- 排除：一次性文案和样式尝试、当前进度、未证实的故障原因、尚未采用的实验方案、聊天流水账。完整产品需求、架构设计和运维细节保留在各自拥有这些内容的文档中，`AGENTS.md` 只写必要约束和阅读入口。
- 替换失效流程时，记录当前可用方式及其适用范围。“旧测试刚移除、以后再决定测试方案”这类历史和待办放在交付说明中；如缺少测试确实影响后续作业，只准确说明当前检查覆盖范围，不保留尚未确定的未来安排。
- 对用户纠正，提炼其真实适用范围。例如，“这个弹窗复用现有组件”不能自动扩大为禁止全项目新增组件；“这次不要增加依赖”不能自动变成永久禁止新增依赖。
- 对暂时绕过检查、关闭校验等排障动作，只有用户明确将其确定为持续适用的约定，且适用范围清楚时才记录；写明必要的条件和结束条件。
- 对阶段性要求写清适用条件，例如“首期版本不接入第三方登录”；阶段切换时复查其是否仍有效。
- 只记录确实存在且有助于导航的目录和入口，避免复制完整文件树、依赖清单或把常规知识写成长篇规则。
- 不把密钥、令牌或完整私密配置写入文件；引用配置模板和获取说明即可。

条目优先表达“何时／哪个范围 → 应该做什么 → 必要时说明原因或入口”。例如：

> 新增删除确认弹窗时，复用 `src/components/ConfirmDialog.tsx`，以保持按钮状态和交互样式一致。

该示例只有在项目实际存在对应组件且约定成立时才能采用。不要套用示例中的技术栈、路径、组件名或目录分层。

## 创建或更新文档

### 生成内容的依据

首次创建或调整文档结构时，先阅读 [AGENTS.md 内容生成参考](references/agentsmd-content-guide.md) 的“定位与格式”和“内容选取表”；涉及命令、子目录、兼容性时再读对应小节。窄范围更新只读取相关小节。

- 使用普通 Markdown，章节按项目需要选择。不要把 Skill 的 YAML 元数据、版本字段或固定模板强加给生成的 `AGENTS.md`；保留已有、确有用途的格式约定。
- 围绕 AI 执行任务需要的上下文和动作编写，补充 README 与现有文档；详细需求和说明通过明确的阅读条件与项目相对链接引用。
- 按阶段检查项目概况、环境与命令、编码规范、测试策略、提交/PR 要求、安全与数据注意事项、部署操作是否有相关依据；只有适用且有证据的内容才写入，不能为了补齐分类发明规范。
- 每条关键命令写清用途和执行目录；条件、参数、环境前提会影响执行时一并说明。区分启动、构建、检查、测试、部署的作用；以实际清单、脚本和 CI 为依据。
- 验证规则应说明何种改动对应哪些检查及其覆盖范围，沿用项目现有要求。文档中指导后续开发运行检查，不等于本次维护文档已运行检查或获得了部署授权。
- 官网示例与官方仓库自己的开发规则只提供写法参考。不得直接套用其包管理器、测试工具、PR 标题格式、全部修改都补测试或交互会话禁止生产构建等具体要求。
- 根目录与子目录规则需要明确作用域；冲突按宿主工具实际加载和优先级处理。官网关于用户要求和就近规则的概述，不应改写成能覆盖平台指令、权限或执行限制的规则。

### 创建

结合阶段表和参考文件的内容选取表，选择必要小节。小节数量和名称不固定；没有依据的内容省略，不为未来阶段制造空栏目。不要把参考文件的检查清单或占位模板原样复制为交付物。

早期项目可以只包含目标、已确认选择和工作边界。成熟项目首次创建时，应覆盖其当前已经形成且有依据的工作方式。用户已授权创建且有可写事实时，直接落盘，不只返回模板。

### 更新

1. 在现有文档基础上，将候选变化分为保留、补充、替换、删除或暂不纳入；不必把这一中间分类输出给用户。
2. 已有规则仍适用时保留。新规则优先合并到相关位置，替换与其冲突的旧描述；确认失效的规则和重复内容应清理，不逐次追加成历史日志。
3. 技术事实与源文件不符时按证据更正。用户制定的工作边界不会因代码中已有违反案例而自动失效；不要为适配当前违规实现或便于任务通过而削弱约束。存在实质性意图冲突时，询问该冲突，继续更新无争议部分。
4. 根文件保留公共规则。模块规则只在确有差异时放入对应子目录，避免复制根规则；每条规则的作用域应清楚。具体加载和优先级依赖宿主工具，不把局部说明写成能覆盖所有上级要求的承诺。
5. 编辑前重新检查文件是否发生变化，保留用户的未提交修改。已有共享引用保持单一信息来源；修改被引用的共享文件需要确认其确属本次范围。

每次功能收尾、技术方案变更、进入新阶段或准备交接时，可进行一次是否需要更新的检查。**检查不等于必须改动**。用户已要求持续维护时，在当前任务收尾执行；本 Skill 本身不创建定时任务，也不承诺未来会自动运行。

## 验证与交付

完成后检查实际文件及差异：

- 根目录定位正确；根 `AGENTS.md` 已创建或读取；变更范围与任务一致。
- 每条新增或修改的项目事实有依据；路径和文档链接存在且相对所属说明文件解析到预期位置；未把官网示例或个人机器路径当作目标项目规则。
- 命令与项目清单、脚本或相关配置一致，执行目录、条件和验证范围足够明确；区分“已定义”与“本次运行通过”。不要虚构 `test`、`lint` 或部署脚本，不为了维护说明执行有副作用的命令。
- 阶段重点得到覆盖，仍适用的既有规则被保留，失效内容被替换或删除，没有互相冲突的约定、空模板或临时进度。
- 同样的事实再次调用时应能保持不变，避免纯改写措辞、增加时间戳或重复规则。

用简短中文交付：目标项目与文档链接；阶段及主要依据；结果是创建、更新还是无需修改；主要变化和实际做过的验证。只有影响使用的未知项才说明；不声称运行了未执行的检查。若当前会话后续行为受重要规则变化影响，重新读取相关说明再继续。

官方来源、适用边界与写法示例见 [AGENTS.md 内容生成参考](references/agentsmd-content-guide.md)。阶段划分、证据核对与维护节奏是本 Skill 的工作方法，不是官方规定的阶段模型。日常本地维护无需重复联网；只有用户要求刷新参考，或需要确认宿主工具的加载行为时，才查询相应官方资料。
